# Remote USB Agent Architecture

The long-term product boundary is a standalone `moonlight-usb-agent` process.
Moonlight owns per-host policy, consent, and presentation; the agent owns USB
enumeration, exporter/backend permissions, the authenticated reverse tunnel,
leases, and teardown. Sunshine only talks to its local loopback USB/IP bridge,
which is the only component that invokes `usbip-win2`.

```text
Moonlight UI/policy --(local IPC, bearer token)--> moonlight-usb-agent
                                                     |
                                                     +-- platform USB backend
                                                     +-- broker HTTPS + TLS tunnel
Sunshine usbip-win2 <-- 127.0.0.1 bridge ----------+
```

## IPC contract

The first agent slice uses one JSON object per line over a restricted
`QLocalServer` endpoint. The client must send `{"op":"hello","token":"..."}`
first. The token is generated by Moonlight for one agent lifetime and is never
sent to Sunshine. Messages are capped at 64 KiB and only one authenticated
client is accepted at a time.

Requests are `enumerate`, `start` (with a stable device id and host/session
parameters), and `stop`. Events are `ready`, `devices`, `opening`, `opened`,
`stopped`, and `error`. The client carries a monotonically increasing decimal
generation on every request and accepts only matching events, so a late event
cannot reopen a newer lease.

Moonlight snapshots the paired host address, HTTPS port, pinned Sunshine
certificate, client certificate/key, client identity, and display name into
the authenticated local `start` request. The agent then fetches a one-shot
broker capability and owns the complete data-plane sequence:

```text
broker capability -> TLS -> HELLO -> CAPABILITY -> OPEN
                  -> libusb claim -> OPEN_OK -> USB/IP PDU
```

The key material is bounded, transferred only over the owner-restricted local
socket, and is neither logged nor persisted. Keeping broker input as an
explicit value object means the agent does not read Moonlight's settings or
depend on `NvComputer`/`IdentityManager` internals.

## Migration rule

The existing Qt coordinator remains an opt-in compatibility implementation for
the first Windows loopback proof. Its `RemoteUsbPlatformAdapter`, shared C
session, USB/IP PDU codec, and TLS framing are the agent's reusable core. Once
the IPC client is wired into `Session`, the in-process coordinator is removed
from production builds rather than becoming a second transport.

Windows uses a libusb/native backend in the agent and keeps usbip-win2 on the
Sunshine side. Linux can provide a usbip-host-backed backend, and Android uses
the user-space `UsbManager` implementation. iOS is unsupported until the OS
permits the required USB host/export operations.

## Qt integration

Build the Qt client from the top-level project with
`CONFIG+=remote_usb_agent CONFIG+=remote_usb_libusb`. This adds
`RemoteUsbAgentClient`, builds the Agent before Moonlight, and places it beside
the application executable (`Contents/Helpers` on macOS). At runtime Moonlight
discovers the packaged Agent automatically and starts one process per streaming
session. `MOONLIGHT_REMOTE_USB_AGENT_PROGRAM` remains available only as a
developer override for an alternate Agent executable.

When a stream opens, the Agent enumerates devices but does not claim one. The
streaming overlay exposes a **USB Devices** submenu. Selecting a device is the
per-session consent action; selecting the connected device again releases it.
Hubs and devices with isochronous endpoints are visible but disabled until
their backend support exists. A disconnect always sends `stop`, and the Agent
lease timeout remains the final recovery path if Moonlight disappears.

The legacy in-process coordinator is reachable only when explicitly enabled
with `MOONLIGHT_REMOTE_USB_ENABLE=1` and no Agent can be discovered. It is a
compatibility path for backend migration, not the production transport.

## Cross-repository contract verification

Sunshine's `RemoteUsbBrokerServer.MoonlightWireContractRoutesImportSubmitAndUnlink`
test is the executable compatibility boundary for the Moonlight shared-core
wire format. It performs the TLS HELLO exchange, sends the client CAPABILITY,
accepts Sunshine's OPEN, returns OPEN_OK, and then drives the loopback endpoint
through direct IMPORT, SUBMIT, UNLINK, a late cancelled completion, and CLOSE.

The loopback bridge intentionally replaces the client bus id with a temporary
opaque bus id before advertising it to the host. Tests and host integrations
must use the endpoint returned by Sunshine instead of assuming that the
client's exporter bus id crosses this boundary unchanged.

This contract test does not claim to validate the Windows driver. Exact
`usbip-win2` process arguments and attach/detach state transitions remain
behind Sunshine's host-controller tests; a Windows CI or hardware run is
required to validate the signed driver and UDE device creation end to end.
